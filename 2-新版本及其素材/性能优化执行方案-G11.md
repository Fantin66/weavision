## 梯队一：低风险 · 高收益

### 【任务1】撤销栈不再克隆 ImageBitmap 缩略图

**根因**
- `state.js:211` `MAX_HISTORY=60`
- `state.js:213` `cloneCanvasState()` 对 `{items,links,camera,previews}` 做 `structuredClone`；其中 items 的 fileCard 项带 `.thumb`（ImageBitmap）。
- 按结构化克隆规范，ImageBitmap 是**深拷贝解码数据**，每步操作产生一份全量缩略图副本，最多 60 份常驻内存。
- `state.js:222-225` `pushHistory`；`state.js:228-235` `undo`（231 再 clone）；`state.js:238-245` `redo`（241 再 clone）。
- `.thumb` 写入点：`app.js` restoreFiles（`file.thumb=bmp`）、`interaction.js:958`；读取点：`render.js:2132`。

**操作步骤**
1. 在 `cloneCanvasState`（state.js:213）克隆前，遍历 items，把 fileCard 项的 `.thumb` 临时置 `null`，记录这些项的 id（或直接靠 fileId）。
2. `structuredClone` 后，对克隆出的快照**不恢复 thumb**——快照只保留 `fileId`（fileCard 本来就有）。
3. `applySnapshot`（state.js:216 附近，restore 时）恢复后，遍历当前 items，对 fileCard 项按 `fileId` 从 `state.files` 重新引用 `thumb`（files 上的 thumb 在 restoreFiles 时已重建）。若对应 file 无 thumb（未恢复），保持 null，render 时走占位逻辑（render.js:2132 已有 else 分支）。
4. 验证 undo/redo 后图片仍正确显示。

**验收**
- 用含 20+ 图片的画布连续操作 60 次，内存不再阶梯式增长。
- undo/redo 多次后图片缩略图不丢失、不空白。

**风险**：低。图片内容本就在 files 里，随时可重新引用。注意 applySnapshot 后要触发一次 thumb 重新挂载。

**依赖**：无。

### 【任务5】存档防抖

**根因**
- `app.js:18` `saveState()` 内 `localStorage.setItem("board-state",JSON.stringify(data))`——全量序列化整个 state（所有项目/画布/items 文本）。
- 被 `state.js` 几乎每个操作调用（139,155,163,171,181,187,192,197,201,235,245）及 `app.js` 各处（264 主题、360 resize、424 keydown）。
- 无防抖，每次小操作都同步序列化+写 localStorage，主线程阻塞。

**操作步骤**
1. 在 `app.js` 顶部引入防抖版（见文末 `debounce`）。新增 `const saveStateDebounced = debounce(saveState, 1500)`。
2. 将 `state.js` 与 `app.js` 中**非关键路径**的 `saveState()` 调用替换为 `saveStateDebounced()`（建项目/画布/文件、改名、拖拽结束、undo/redo 等）。
3. **关键路径保持立即 flush**：`beforeunload`、切换项目/画布前（确保旧画布状态落盘）、`export` 前、应用退出前——这些调原 `saveState()` 或 `saveStateDebounced.flush()`。
4. 在 `app.js` 末尾 `window.addEventListener("beforeunload",()=>saveState())` 确保兜底。

**验收**
- 连续快速操作（建10个画布）只触发 1-2 次序列化；松手后 CPU 不尖峰。
- 切画布/关窗口前状态已落盘。

**风险**：低。断电可能丢最后 1-2 秒，有 beforeunload + 30s 自动保存兜底。

**依赖**：建议在任务2之后做（拖拽攒帧后 saveState 才不会和重绘叠加）。

### 【任务6】localAvoid 只检查附近一圈

**操作步骤**

2. `state.items.find(i=>i.id===id)` 改用开头构建的 `idMap`（见任务11，若无则本任务内临时建一个 `Map`）。
3. 保留 10 轮迭代上限和连锁检查逻辑，仅缩小每轮候选集。

**验收**
- 拖材料卡/便签在 200+ 元素画布上不再顿挫。
- 推开效果与原来一致（不重叠、留间隙）。

**风险**：低。只缩范围不改逻辑。注意 padding 要够大，避免漏推该推的。

**依赖**：与任务11共享 idMap，建议一起做。

### 【任务7】mindNode 找孩子用索引而非全表 find

**根因**
- `interaction.js` `onPointerMove` move 分支：`collectKids` 递归中对每个 `cid` 调 `state.items.find(i=>i.id===cid)`，每找一个 O(n)。20 个孩子=20 次 O(n)/帧。

**操作步骤**
1. 在 `state.js` 增加 `let idMap=new Map()`，在每次 render 或 state 变更后重建：`idMap=new Map(state.items.map(i=>[i.id,i]))`（或在 applySnapshot/数据变更点重建）。
2. `interaction.js` 的 `collectKids` 改用 `idMap.get(cid)`。
3. 同样替换 `localAvoid`（任务6）、`hitTest`（任务15 前置）等其他 `state.items.find` 热点。

**验收**
- 拖层级深（20+ 后代）的思维节点不再卡。

**风险**：低。注意 idMap 重建时机，避免用过期引用。

**依赖**：无。但为任务6/15提供基础。

### 【任务9】render 合并多次 items 遍历

**根因**
- `render.js` 中 `for(const it of state.items)`/`for(const _it of state.items)` 出现 10 次（行 65,74,115,162,165,456,975,1016,1046,1049）。单次 render 对全部元素扫 10 遍。

**操作步骤**

**风险**：中。限制了"同时摊开多个网页"，用全屏单看补偿。

**依赖**：无。

### 【任务11】便签装饰预渲染缓存

**根因**
- `drawNote`（render.js:1220+）每帧每便签创建多个 `createLinearGradient`（1240,1242,1256,1261,1269）+ `shadowBlur`（1236）+ `markdownLines`+`wrapLines` 逐行 `measureText`（1294-1302）。内容/尺寸未变也重做。

**操作步骤**
1. 为每个 note item 维护缓存 `{key, canvas}`，key = `id|text|w|h|color|dark|selected|stylePreset|fontPreset|zoom 档位`。
2. key 不变时，`drawNote` 直接 `drawImage(缓存canvas, x, y)`。
3. key 变化时重绘缓存 canvas（尺寸按 `dpr*zoom` 取整避免亚像素抖动），更新 key。
4. zoom 变化分档（如每 0.1 一档）缓存，避免缩放频繁失效。
5. 内存控制：缓存总数超阈值（如 200）时 LRU 淘汰。

**验收**
- 50+ 便签画布拖拽/动画明显更跟手。
- 便签内容修改后立即更新；改主题/选中态正确重绘。

**风险**：中。key 漏字段会画面变旧。缓存占内存（有上限）。zoom 分档要覆盖。

**依赖**：无。可独立做。

### 【任务12】ResizeObserver 防抖

**根因**
- `app.js:1855` `new ResizeObserver(()=>{resize();}).observe(board)`。resize() 触发 render。动画/漂移/覆盖层位置变化可能引发连环。

**操作步骤**
1. 回调包防抖：`new ResizeObserver(debounce(resize, 150)).observe(board)`。
2. 确认 `resize`（app.js 中）内部已有 `requestRender` 或加之。

**验收**
- 动画期间无额外 render 抖动；窗口真正缩放后正常重绘。

**风险**：低-中。

**依赖**：用文末防抖工具。

### 【任务13】主题事件防抖

**根因**

- `app.js:264,284` mediaQuery 主题回调也 render+saveState。

**操作步骤**

3. 保留"首次主题读取"立即生效（不走防抖）。

**验收**

**风险**：低-中。

**依赖**：任务5（saveState 已防抖则此项只剩 render 防抖）。

## 梯队三：大工程 · 留到最后

### 【任务14】render 视口裁剪（先做）→ 脏区域（后做）

**根因**
- `render.js:35` `render()` 每次 `clearRect` 全画布 + 全量遍历。无可见性裁剪。

**操作步骤（阶段A：视口裁剪，先做）**
1. 在 `render` 遍历 items 前，算出当前视口世界矩形 `viewRect = {x:camera.x, y:camera.y, w:W/camera.zoom, h:H/camera.zoom}`。
2. 每个 item 先 `itemBounds(it)`，与 viewRect 相交才 `drawItem(it)`；不相关跳过。
3. 连线（drawLinks/drawMindConnections）同理裁剪：两端都在视口外的跳过。

**操作步骤（阶段B：脏区域，后做，可选）**
1. 记录上一帧 items 的 bounds，对比本帧变更，只重画变更区域+受影响连线。
2. 复杂度高，建议仅在阶段A 仍不满足时再考虑。

**验收**
- 视口外元素不画；放大到只看局部时 render 耗时与可见元素数成正比，而非总数。

**风险**：高（阶段B 尤甚）。裁剪边界、连线跨视口、阴影溢出都要处理，否则残影。

**依赖**：任务7 的 idMap、任务9 的遍历整理做完后再做更稳。

## 附：防抖工具函数

放 `app.js` 顶部（或新建 `utils.js` 并在 G11.html 中 app.js 之前加载）：

```js
function debounce(fn, wait){
  let t=null;
  const d=function(){const ctx=this,args=arguments;
    if(t)clearTimeout(t);
    t=setTimeout(()=>fn.apply(ctx,args),wait);
  };
  d.flush=function(){if(t){clearTimeout(t);t=null;fn.apply(d,[]);}};
  d.cancel=function(){if(t){clearTimeout(t);t=null;}};
  return d;
}
```

关键路径调 `debounced.flush()` 强制立即执行。
